A harness for media-heavy work

3PT is an agent harness for any business that produces a lot of images. It learns from the team's yes and no answers, then rewrites its own rules, context policy, guardrails and tools. For the hackathon we show it on one example: a construction firm's site photos across several jobs and years. The photos are the data. The harness is the product.

Hackathon goal · Statement one, Recursive Harnessing

A harness for media-heavy work that starts generic and rewrites its own rules, context policy, guardrails and tools from feedback. We demo it on a construction firm's lifetime of site photos. Every finished project becomes a retrospective, a ranked list of opportunities, and a playbook for the next job. Every version lives in MongoDB.

Generic core, one example

The harness is general. The demo is construction.

The proof that it is general: harness v0 knows nothing about construction. It only describes an image, its date and its source. Every construction field, rule and tool in the demo is something the harness added to itself.

How it learns

First the old data. Then every new photo makes it better.

Phase 1 · backfill Ingest the firm's old jobs

Read every old photo once. Read the old activity log: searches, exports, taps. Organize, score, snapshot. Many versions in a short time.

→
Phase 2 · live Each new photo is a test

A new photo arrives. The harness files it with the current version, checks its rules, and sends reminders. Surprises feed the next loop.

Every harness state is a snapshot. A version document never changes after it is saved. Rollback moves a pointer back to an older version.

Per project

Every job ends in a retrospective. Every retrospective ends in a playbook.

Media is filed under the project it belongs to. When a job closes, the harness looks back at its photos and its activity, ranks what could have saved time or avoided cost, and writes the reminders and prompts for the next job.

Which problem statement

Statement one. The harness changes all four parts of itself.

The brief names what should evolve: rules, context policies, guardrails and tool access. A new extraction field alone covers only the first. Each harness version is one MongoDB document with all four parts, and the loop proposes a diff to it.

The loop, in site terms

Three points, each with a job

1

Plan

Read one-off requests, failed searches and "no" taps. Group them into plan items. Pick the one that matters most.

2

Build

Ship one change: a rule, the context policy, a guardrail, a tool, or an automation for a repeated task. Snapshot it as a new version. Re-read affected photos once if a rule changed.

3

Instrument

Score it: useful answers, reminders acted on, automations kept, cost per photo. If the score drops, roll back.

Stress test

Hard questions about construction

Open
Where does "time saved" come from?

From event timestamps where the log has them, such as search start to export. Otherwise a minutes value the user sets. Show which one each number uses. Never present an estimate as measured.

Open
Can photos alone support a retrospective?

No. A retrospective needs outcomes: reopened walls, punch-list items, delays. Log them as events. The demo seeds 3 reopened walls on job 1 and labels them synthetic.

Open
Where does a usage history come from?

A new install has none. For the demo we seed a past activity log for jobs 1 and 2 and label it synthetic. In a real install, the log starts on day one.

Open
Is this too much for one day?

Show one repeat, one one-off and one live photo. The ladder thresholds (3 and 3) are starting values, not tuned.

Decided
Will reminders annoy people?

Every dismiss counts as a "no" and moves the task back down the ladder. Automations need a person's approval.

Open · first 30 min
Where do real site photos come from?

Candidates: iVISION-2DCD, a long-term construction change dataset, and ConPR, repeated captures of one active site. We have not checked their licence or download yet. Using data without the rights means disqualification, so the licence check comes before any code. Fallback: Wikimedia Commons photos under public domain, CC0 or CC BY only, credited in the README, with dates and units assigned by us. Say so in the video. A lifetime needs photos from at least two or three different sites, and ConPR covers one.

Open
How does a photo get its unit and level?

On real sites this is the hard part. OpenSpace solves it with 360° walks and floor plans. For the demo, the upload form sets the unit. Be honest about it.

Decided
Why not just use OpenSpace?

They measure this job against the plan. We make the photo archive answer questions later, across jobs. Photos from any phone work.

Decided
Can the harness wreck the index?

Every harness version is a checkpoint. A score drop rolls back on its own. A person approves each new field.

Open
Can a vision model see "open wall" reliably?

Test it on 20 photos before building the rest. If it fails, pick a field it can see, such as "exposed pipe" or "ceiling open".

Open
Who pays?

Guess: a mid-size general contractor. The project engineer runs it, and the ops lead wants lessons across jobs. Nobody has confirmed this yet.
