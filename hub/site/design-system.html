One design system for the monorepo: six pieces, three directions, one decision.

This page holds everything Patrick and Yash need to choose the 3PT design system: the invariants that hold under any direction, six pieces with three candidates each, three canonical directions composed from those pieces, the bases for judging motifs against the ICP, and a promenade for deciding. The chosen composition is then compiled into tokens for the hub, the web app and PWA, and the Swift inspector.

0 · where we standTwo systems already exist. This page ends that.

Nothing here starts from zero. The repo already wears two visual systems written on the same day, and neither knows the other. The design system has to absorb both or retire one, and it has to do so with tokens that a Swift app can read, not only a stylesheet.

1 · invariantsWhat holds under every direction

These are decided by this proposal unless someone objects in the promenade. They are the bases against which every motif and every piece is judged, and they do not change when the direction does.

I1 · Three tiers of tokens

Primitive (a hue and a step, never used directly), semantic (a role: what the colour is for), component (which role a part of a component reads). A leaf or a view only ever names the semantic or component tier. Adding a colour means adding a role, not a hex.

I2 · Dark and light are peers

Every semantic token has a value in both sets. A direction that cannot show both is not a candidate. The mode is never part of a token's name; the set is swapped, the names stay.

I3 · The three points keep their slots

Plan, Build, Instrument appear in that order, each with its own hue slot (point.plan, point.build, point.instrument). Those hues never colour anything else. The triangle mark is the wordmark on every surface.

I4 · Status is not category

ok, warn, alert colour provenance and outcomes only. Clusters, phases, trades, and directions never borrow them. Status never relies on hue alone: it pairs with a glyph or a word (the hub's ○ ◐ ● ladder already does this).

I5 · Every figure wears provenance

DERIVED, AUTHORED, TO CONFIRM is a fixed triple aliased onto the status hues. It must be legible at 8.5px mono in every direction and mode; the contrast table below checks it.

I6 · Photos are neutral

A thumbnail gets a one-pixel line frame and no tint, and it is never larger than the record beside it. The hero of any surface is never a photograph. This keeps the product on the right side of the image-analyzer ban and keeps the accent free.

I7 · One accent per screen

One hue says "this is new, this is picked, this is where you are." Everything else is ink, muted, line, and surfaces. The direction chooses the hue; the rule stays.

I8 · One glyph set, three weights

The nav.js glyph paths are the iconography on every surface. A direction changes only stroke weight and caps. In Swift the same paths ship as custom symbols so weight follows text.

I9 · Nothing web-only carries meaning

No backdrop blur, no gradient text, no filter as a signal. Anything that means something must be drawable with a colour, a path, and text, because SwiftUI will have to draw it.

I10 · Tokens have one source

A single tokens file in the repo generates the CSS for the hub and the web app, the asset catalog and Swift enum for the inspector, and the manifest colours for the PWA. Hand-edited hex in any of those is a lint failure.

Spelling per surface

  • JSON (source): bg.canvas
  • CSS: --bg-canvas
  • Swift: TPT.bg.canvas backed by asset bg/canvas with light and dark appearances
  • Tailwind, if the web app uses it: bg-canvas reading the CSS variable

Rules

  • Mode never in the name (no --bg-dark).
  • No colour words above the primitive tier.
  • Numbers only at the primitive tier (gray.900).
  • Components reference semantics, never primitives.
  • Type, space, radius, motion tokens follow the same shape: type.display, space.4, radius.card, motion.fast.

Migration cost

  • 3pt.css: 34 variables renamed once; leaves updated by search and replace.
  • nav.js: five hardcoded hex values become var() reads.
  • direction.html: stays as written (it is a dated proposal), or is re-expressed if it becomes the lander.

3 · dark and lightAccessible patterns for both modes

Mode selection

color-scheme on the root. Default follows prefers-color-scheme; a data-theme attribute overrides it and is persisted (tpt_theme in the browser, the same preference key in the app). The PWA declares two theme-color metas, one per scheme. SwiftUI reads the same stored preference into preferredColorScheme. This page does exactly this; try the controls above.

Elevation

In dark, a raised surface is lighter than the one below it, never darker, and shadows are optional. In light, a raised surface is separated by a line, with shadow allowed. bg.canvas → surface → raised encodes this; a component never invents a fourth step.

Accent in the dark set

The dark accent is lighter and less saturated than the light accent, and it carries its own fg.on-accent (dark ink on a light accent). Reusing white from the light set is the most common failure in the two existing systems and the contrast table catches it.

Contrast targets

WCAG 2.x ratios, computed live below: 4.5:1 for body ink, muted ink, accent-as-text and status-on-soft; 3:1 for faint labels, strong lines and the point hues as marks. APCA Lc 60 for body is the stricter check to add once the tokens file exists.

Focus, motion, forced colours

Focus ring: 2px accent, 2px offset, both modes. prefers-reduced-motion zeroes every duration. forced-colors: active brings borders back on anything that relied on a fill. Hit targets 44pt on the PWA and iOS.

Never colour alone

Every status has a glyph or a word beside the hue. Yes and no marks on tiles are text. Keep and cut are labelled. The version diff uses added and struck text, not green and red fills alone.

4 · piecesSix pieces, three candidates each

A direction is a composition of six pieces. Each piece has three candidates, one per direction, and they can be recombined: the compiled specimen further down takes any mix. Pieces are the unit of decision in the promenade; directions are the shortcut for taking all six from one source.

5 · three canonical directionsThe major directives, composed

Each direction below is all six pieces from one source. The specimen is the same markup every time: only tokens change. Read them with the ICP lens in mind: the working synthesis in docs/08-icp-directions.md is to build the harness for the pipeline team and dress the lander for the interior studio, which pulls in two different visual directions at once.

6 · contrastEvery pair, every direction, every mode

DERIVED Ratios computed at load from the token values above with the WCAG 2.x relative-luminance formula. A direction fails the mode gate if any pair is below its threshold. Thresholds: 4.5 for text, 3 for large text, UI edges and marks, 1.3 for hairlines (a visibility floor, not a WCAG rule).

8 · component libraryOur own components, and what they read


We build our own library rather than adopting one, because the inspector, the hub and the app share a small vocabulary that no third-party kit has: provenance badges, the version diff, the ladder, the stream switch, the proposal card. Twelve components cover everything the demo needs. Each is a record: anatomy, tokens consumed, states, and its Swift twin.



  
Naming
  • CSS: .tpt-button, .tpt-button.primary; parts as .tpt-card-title. Flat, no BEM underscores.
  • Swift: TPTButton, TPTCard; variants as enums, TPTButton(.primary).
  • Every component lives in design/components/ as one HTML fragment plus one Swift file with the same name. The hub renders the fragments as its own component sheet.

  
Rules
  • A component reads component-tier tokens, which read semantics. It never names a hue.
  • Every component has a light and a dark screenshot in its record before it is used on a surface.
  • States are enumerated: default, hover, focus, active, disabled, and for provenance and status the three fixed values.
  • A new component needs a reason the twelve cannot cover, written in its record.

9 · motifs against the ICPWhat is acceptable, and on what basis


The ICP is still being dialled in (docs/01-icp.md, docs/08-icp-directions.md). Motifs speak to industries: marking paint reads as a jobsite, a title block reads as a studio, a rail of coloured points reads as an engineer's console. The bases below say what any motif must satisfy regardless of industry; the matrix says how each direction speaks to each ICP direction, so the design decision can follow the ICP decision instead of preceding it.


Bases: every motif must pass all seven




#BasisWhy


B1The hero is never a photograph, and no photo is larger than the record beside it.Image analyzers are banned. The eye must land on the harness, not the corpus.


B2One accent per screen; status hues never colour categories; the three points keep their slots.I3, I4, I7. A motif that needs a second accent is two motifs.


B3Provenance badges legible in the motif's own colours, both modes.Tallies are never typed. The badge is the credibility of every number.


B4Same glyph paths on every surface; the motif may change stroke only.I8. Swift gets the same symbols.


B5Drawable with colour, path and text.I9. The inspector is native.


B6Buildable today: fonts available now and self-hostable; no custom illustration.Due 5:00 PM. A motif that needs an illustrator is a roadmap item.


B7Distinct from the partners in the room: no MongoDB green accent, no black-on-black Vercel base.The judges see forty submissions on those two palettes.

10 · the promenadeHow Patrick and Yash decide


A promenade, not a vote: walk the pieces in order, record a pick per piece, then compile. The ballot is stored in this browser under tpt_ds_v1; it does not sync. Export as text and paste it to the other person, or fill both columns together on one screen.



  
Gates (must pass, in order)
  1. Both modes pass the contrast table.
  2. All seven bases in section 9.
  3. Every piece has a Swift translation in section 7 that costs less than an hour.
  4. Fonts load from a CDN now and can be self-hosted before the PWA goes offline.

  
Criteria (score 1 to 5, weighted)
  1. Fit to the ICP we choose (the matrix, ×3)
  2. Reads as harness, not analyzer, not dashboard (×3)
  3. Holds up dense: the inspector is tables and diffs (×2)
  4. Warmth in a three-minute demo (×2)
  5. Both modes hold without a redesign (×2)
  6. Distinct from the partners in the room (×1)
  7. Build cost before 5:00 PM (×1)




Procedure
    

  1. Round 1, ten minutes, apart. Each principal fills their column: one pick per piece, an overall direction, one sentence of reasoning. Score, do not describe taste.
    2. 

  2. Round 2, ten minutes, together. Lock every piece where the columns agree. For each disagreement, each side names the criterion number that decides it. If still split, the lane owner decides: shape, motion and iconography go with the Swift and shell lane; colour, type and motif go with the ICP and lander lane. This tie-break is itself a proposal; strike it if it is wrong.
    3. 

  3. Round 3, five minutes. Set the compile row to the locked picks, read the compiled specimen once in each mode, export, and paste the export into the decision record at the bottom. Commit as docs: design system decision with both names.
    4. 

  4. After. Write design/tokens.json from the export, generate hub/site/3pt.css and move the nav shell onto tokens, start Tokens.xcassets for the Swift lane. Update this page's status line from proposal to decided.
    5.
